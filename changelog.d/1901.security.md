One installation can no longer read or overwrite another's dashboard data (#1901). The cloud dashboard used a single shared `CLOUD_DASHBOARD_API_KEY` for every route and let the caller name the installation, so anyone holding the key could register, push metrics for, read, or stream any installation, and a bad id was only rejected for length. Each installation now has its own random token, issued once by the operator at `/register` and stored only as a hash, and the installation id comes from the token: `POST /metrics`, `GET /metrics/{id}` and `/ws/{id}` refuse any other id (403), unknown ids and bad tokens fail closed (401), and `"rotate": true` invalidates an old token. `CLOUD_DASHBOARD_API_KEY` is now the operator credential (register, rotate, read any installation). **Behaviour change:** installations that pushed with the shared key must be given a token (`X-Installation-Token`); until then set `CLOUD_DASHBOARD_ALLOW_SHARED_KEY=true` to keep the old push behaviour. See `docs/cloud_dashboard.md`. Per-installation state now uses separate key prefixes (`cloud:metrics:`, `cloud:credential:`, and the existing registration prefix), so an installation id chosen to look like another's key (for example `credential:victim`) cannot overwrite that installation's credential or forge a registration; metrics have a 60-second TTL, so nothing needs migrating.
