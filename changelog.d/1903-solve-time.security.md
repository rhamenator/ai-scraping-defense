The built-in CAPTCHA now treats a too-fast solve and a missing client proof as bot signals that ask again instead of blocking (follow-up to #1903). A correct answer that arrives faster than `CAPTCHA_MIN_SOLVE_SECONDS` (default 1.5, 0 disables) or without the proof the page computes from the challenge id and the answer (`CAPTCHA_REQUIRE_PROOF`, default true) fails with `{"success": false, "retry": true}`: no token is issued, no success is logged, and the page loads a fresh question with a polite message. Nothing is blocked or labelled and no hidden field or control is added, so screen-reader users and password managers are unaffected. The proof is an open-source function and can be copied, so it only filters clients that post the form without running the page; the minimum time is the check that holds whatever the client. **Behaviour change:** API clients that post to `/solve` directly now need the proof or `CAPTCHA_REQUIRE_PROOF=false`, and a solve faster than 1.5 seconds is retried.
