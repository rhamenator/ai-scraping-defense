Blocks made from the admin UI, by a signed webhook, or by the tarpit now actually take effect at the edge (#1902). The edge reads the key `<tenant>:blocklist:ip:<ip>` in the blocklist database (`REDIS_DB_BLOCKLIST`, default 2), which only the escalation engine wrote. The admin UI and the signed webhook added the address to a Redis set the edge never reads (the admin UI in the default database), and the tarpit wrote `<tenant>:blocklist:<ip>`, so those blocks returned success and did nothing. All writers now go through `src/shared/blocklist_store.py`: one key, one database, TTL for automated blocks (tarpit, engine) and no expiry for blocks an administrator or a signed webhook asked for, IPv4-mapped IPv6 addresses stored as IPv4 (the edge now normalises `::ffff:a.b.c.d` the same way), and success reported only after the key is read back. Unblocking removes the same key plus any legacy copy. Existing blocks in the old shapes are moved to the real key the first time the admin UI connects (`migrate_legacy`). The admin blocklist list and statistics now count the keys the edge enforces. **Behaviour change:** blocks that were previously ineffective become effective on migration, so review the blocklist after upgrading; see `docs/blocklist_storage.md`. An expiring block (tarpit, engine, migration) never replaces a permanent one, a lifted block is also cleared from the old default-database set so migration cannot bring it back, and legacy tarpit keys that are about to expire or already have are migrated with a bounded expiry or skipped instead of becoming permanent.
